# aict1 迁移 Vue 3 + @ruinb0w/ui —— 方案

> 状态：**方案，未动任何代码。**
> 日期：2026-10-29
> 参照：exp1 已在 2026-10-05 做完同一件事（React 19 → Vue 3 + Pinia + `@ruinb0w/ui`），
> 过程记录在 `~/Workspace/exp1/.pi/plans/2026-10-05-vue3-migration-feasibility/`。
> 本次是把那份路线缩小到一个 1/4 规模的代码库上重放，并把 exp1 实测到的坑提前埋掉。

## 0. 结论

**能做，工作量小。** 这不是架构手术，是把 **≈3.2k 行视图层 + 1k 行 store** 重敲一遍：

| 类别 | 量 | 处置 |
|---|---|---|
| 视图层 `.tsx` | 14 文件 / 2,172 行 | 重写为 `.vue` |
| 样式 `index.css` | 2,296 行 | 大幅裁剪（见 §5） |
| zustand store | 5 文件 / 1,003 行 | → Pinia |
| hooks | 2 文件 / 75 行 | → 2 行模板 / 库自带 composable |
| **框架无关代码** | **≈985 行** | **零改动** |

三个让这次迁移比 exp1 轻松的事实，见 §2。

相比之下 exp1 是 14k 行视图层、89 个 tsx、20 个 hook、5 个 store、25 个测试文件。这次没有路由层、
没有组件测试、没有复杂表单弹窗。

## 2. 三个"免费"的利好

### ① Tailwind 是幽灵依赖，可以直接删掉

`vite.config.ts` 挂了 `@tailwindcss/vite`，`package.json` 装着 `tailwindcss@4`，但：

- `index.css` 里**没有任何** `@import "tailwindcss"` / `@theme` / `@apply`
- 275 个 `className` **全是手写类名**（`.search-box` `.word-title` …），有 0 个工具类

也就是说 Tailwind 一行都没生效。而 `@ruinb0w/ui` 的硬规则是「不引入 Tailwind，不做 `@theme` 适配层」——
本来会冲突的事，在这里**直接删依赖即可**，不需要任何折中。

### ② aict1 的配色 == 库里现成的 `exp1-dark` 主题，逐值对得上

| aict1 `:root` | `exp1-dark` |
|---|---|
| `--color-bg: #1b1b1f` | `--bg-page: #1b1b1f` |
| `--color-bg-secondary: #202127` | `--bg-card: #202127` |
| `--color-primary: #ffffff` | `--text-primary: #ffffff` |
| `--color-secondary: #a1a1aa` | `--text-secondary: #a0a0a0` |
| `--color-accent: #f56565` | `--color-primary: #f56565` |
| `--color-border: #2d2d3a` | `--border-default: #2a2a30` |

**不新增主题**，`document.documentElement.dataset.theme = 'exp1-dark'` 直接用；哪天要独立皮肤再让库里加
`dict-dark`（`gen-tokens` 会校验四套主题键集合一致，加一个主题是一次性成本）。

密度：桌面 400×600 窗口用 `data-density="default"`（36px 控件），Android/iOS 构建用 `"touch"`（44px）——
`getPlatform()` 已经有了，一行 if。

### ③ 库里的组件几乎覆盖了本项目的全部基础件

`@ruinb0w/ui` 有 42 个 `R*` 组件 + `useConfirm` / `useOnlineStatus` / `useOverlayLayer`，
本次能对上的见 §4。真正「库没有」的只有三样：桌面无边框标题栏、Toast、复习翻转卡片。

## 5. CSS 策略（真正的体力活）

`index.css` 2,296 行是**唯一的样式来源**，不能一次性扔掉。分两步：

**第一步（阶段 1，半天）：把 `:root` 换成 token 别名垫片，页面照旧能跑。**

```css
:root {
  --color-primary:   var(--text-primary);
  --color-secondary: var(--text-secondary);
  --color-accent:    var(--color-primary);
  --color-bg:        var(--bg-page);
  --color-bg-secondary: var(--bg-card);
  --color-border:    var(--border-default);
  --color-error:     var(--color-danger);
  --color-success:   var(--color-success);
  --color-warning:   var(--color-warning);
  --color-info:      var(--color-info);
  /* 间距/圆角同样映射到 --space-* / --radius-sm|md */
}
```

这样 2,296 行老 CSS 一行不改就有库的配色与尺度。**这是纯过渡垫片，收尾时删掉。**

**第二步（阶段 4–6，随页面重写逐块删）：** 每写完一页，把对应 CSS 段整段删除：

| CSS 段 | 行量级 | 归宿 |
|---|---|---|
| `.bottom-nav` / `.nav-item` | ~40 | 删（`RTabBar` 自带） |
| `.toast-*` | ~75 | 保留，改读 token |
| `.error-boundary*` | ~80 | 删（`RErrorBoundary`） |
| `.network-indicator` | ~20 | 删（`ROfflineBanner`） |
| `.search-box` / `.search-input*` | ~50 | 删（`RInput`） |
| `.query-result` 加载/空/错态 | ~60 | 删（`R*State`） |
| `.word-*`（音标/词性/例句/近反义/批注） | ~400 | **保留**，改读 token |
| `.review-*`（翻转卡片） | ~300 | **保留**，改读 token |
| `.title-bar*` | ~60 | **保留** |
| `.app` / `.main-content` / `.page-*` | ~80 | 保留（`Transition` 类名不变） |
| 其余（favorites/history/settings/grammar 各页） | ~1,100 | 随页面重写删除，目标 **≤800 行** |

目标：`index.css` 从 2,296 → **≤800 行**，且不含任何十六进制色值与裸 px。

现状是 `currentPage` + `displayPage` 双层 state 手搓 200ms 出场/入场，**没有 URL**。

| 选项 | 做法 | 代价 |
|---|---|---|

## 8. 预埋的坑（exp1 实测，按会踩到的概率排）

**① 响应式 Proxy 直接进 Dexie → `DataCloneError`（几乎必踩）**
`ref`/`reactive` 出来的是 Proxy，Dexie 写库走 structured-clone，遇到 Proxy 直接抛。
本项目受影响点：`wordsStore` 写 `translation`/`example`（编辑态是响应式数组）、
`settingsStore.saveSettings`、`favoritesStore` 的复习字段更新。
**类型检查和构建都抓不到，只有真跑一次写库才暴露。** 起手先加：

```ts
// src/libs/plain.ts —— 响应式对象不能直接进 Dexie（structured-clone 拒绝 Proxy）
export const toPlain = <T>(v: T): T => JSON.parse(JSON.stringify(v))
```

**② `History.tsx:33` 的 `confirm()` 在 Android 上是死的**
`if (!confirm('确定要清空所有历史记录吗？')) return`。Tauri Android WebView 没实现 `onJsConfirm`，
`confirm` 直接返回 false → **清空按钮在真机上永远点不动**。顺手换成库的 `useConfirm()`（`RConfirmHost` 挂在 App）。
没人要求，但一行改动、且是现存 bug，属于「迁移顺手修」的范围。

**③ `vue-tsc` 通过 ≠ `vite build` 通过**
SFC 编译器有 vue-tsc 不检查的限制（典型：`withDefaults` 默认值里引用局部变量）。
收尾两个都要跑。

**④ 受控 input 的 DOM 回滚**
React 的受控 `<input>` 在事件后会把 DOM 值恢复成 state；Vue 用 `:value` + handler 里提前 `return` 时**不重渲染**，
非法输入会留在框里。本项目会踩的是 `Settings` 的 temperature 钳制、`Review` 的分数输入。拒绝分支里显式回写 DOM。

**⑤ 手搓页面动画的 setTimeout 泄漏（现有 bug）**
`usePageTransition.ts` 的两个 `return () => clearTimeout(...)` 一个在 `useEffect` 里（有效），
一个在 `setTimeout` 回调里（**永远不被调用** → 卸载后 `setIsTransitioning(false)` 打空）。
换 `<Transition mode="out-in">` 后这段逻辑整体消失。

**⑥ zustand → Pinia 的响应性丢失**
`const { settings } = useSettingsStore()` 在 Pinia 里会丢响应性，必须 `storeToRefs`。
本项目 82 处左右的 `useXxxStore()` 调用点逐个过一遍。

**⑦ 图标包换名**
`lucide-react` → **`@lucide/vue`**（ui 库的 peerDependency，不是 `lucide-vue-next`），
组件名一致，`className` → `class`。`RTabBar` / `RLucideIcon` 走**名字查表**，需在 `main.ts` 里
`registerIcons({ Search, CheckCircle, Star, History, Settings, WifiOff, ... })`，否则控制台 warn + 显示图标名。

## 10. 不做 / 代价 / 风险

**不做**
- 不动 `src-tauri/**`、`src/utils/{api,tauri,indexedDB}.ts`、`src/types/**`
- 不重构 store 结构、不改 Dexie schema、不改 API 提示词
- 不新增功能，不趁机改视觉（只把硬编码色值换成 token）
- 不搭 React/Vue 共存（`veaury` 桥接双运行时，对 3.2k 行项目纯亏损）

**代价**：约 1 个工作日（AI 辅助、按阶段验证）。翻译是机械的，**成本重心在验证**：
受控输入、写库 Proxy、Pinia 响应性这三处只能靠跑。

**风险**
1. **本项目零测试**（`vitest` 装了但没有一个测试文件）—— 没有 exp1 那种「22 个纯逻辑测试一例不改全绿」的护栏。
   唯一的回归证据是真浏览器冒烟 + 手动写库流程。**如果想降低风险，阶段 0 前先给 3 个纯函数补测试**
   （`isSentence` / 历史裁剪 / 复习等级），成本很小。
2. **窗口是 400×600 无边框**，库组件的默认密度是 36px 控件；`RTabBar` / `RListCard` 在 400px 宽度下的换行与截断要目视确认。
3. `@ruinb0w/ui` 是 `file:../ui` 软链，库改动会直接影响本项目；库没构建（`dist/` 过期）会编译失败。
4. 迁移期间的功能开发会产生双份改动 —— 建议迁移窗口内冻结功能。
5. `AGENTS.md` 不同步就会让下一次会话的 AI 按 React 约定写代码，这一项必须做完。

## 实际抓到的 bug

### ① `indexedDB.saveHistory` 的数据丢失（既有 bug，被 Proxy 问题踩出来）

原实现是 `await clear()` 然后 `await bulkPut()`，**两个独立事务**；`bulkPut` 抛错时清空已经提交 →
历史记录被静默清空、`history.value` 也没更新（异常在赋值之前）。

Vue 版几乎必踩：`history.value` 里的元素是响应式 Proxy，`bulkPut` 直接 `DataCloneError`。
实测：3 条历史 + 查一次词 → 库里只剩 1 条。

修法两处：`historyStore.saveHistory` 写库前过 `toPlain()`；`indexedDBService.saveHistory`
把 clear + bulkPut 收进一个 `db.transaction('rw', ...)`。

### ② 「排查过程中的坑」：先怀疑库，其实是我自己的测试写错了

- 用 `textContent.includes('认识')` 选按钮 → 先命中「不认识」→ 以为掌握度算错了。
- 看 store 状态和库里行数对不上 → 以为有两个 Pinia 实例；实际是**上一次测试把数据改掉了**，
  隔离复现（`store.loadHistory()` → 手动 `saveHistory`）才拿到真正的 `DataCloneError`。

### ③ Dexie 的版本号 = `version * 10`

`new Dexie('DictDB').version(4)` 在 IndexedDB 里是 **40**。往库里塞测试数据时直接
`indexedDB.open('DictDB', 4)` 会 `VersionError`。

# 追加：Windows 模拟器（Android）实机验证（2026-10-29 晚）

环境：Windows 侧 `C:\Android\Sdk`（AVD `api35`，x86_64 / Android 15）+ WSL 侧 `/opt/android-sdk`
（NDK 27.3、JDK 17、Rust 四个 android target 都已装好）。模拟器在 Windows 上跑，WSL 只负责编译，
APK 通过 `adb.exe` 装进模拟器。**这份仓库此前从未构建过 Android**，所以先要把它变成「能构建」。

## 为了能出 APK 改了三处（都是既有缺陷，与 Vue 迁移无关）

1. **`Cargo.toml`：桌面专属依赖挪进 target 段**
   `tauri` 的 `tray-icon` feature（连带 `muda`）在 Android 上编不过 ——
   `muda-0.19.3/src/platform_impl/mod.rs:31: could not find platform in self`。
   `tray-icon` / `single-instance` / `autostart` / `global-shortcut` 四个依赖也只在桌面有意义。
   现在它们放在 `[target.'cfg(any(windows, macos, linux))'.dependencies]`。
   **`lib.rs` 本来就全部 `#[cfg(desktop)]` 了**（tray / autostart / single-instance / 快捷键），
   所以 Rust 代码一行没改。
2. **`capabilities/default.json`：`global-shortcut:default` 挪到 `desktop.json`**
   插件在 Android 上不编译 → 权限不存在 → `tauri-build` 直接报
   `Permission global-shortcut:default not found`。`desktop.json` 本来就带
   `"platforms": ["windows","macOS","linux"]`，把这条权限放进去即可。
3. **npm 端 @tauri-apps/* 升到与 Rust crate 同 minor**（Tauri CLI 会硬校验，不匹配直接拒构）：
   api 2.11→2.12.4、plugin-dialog 2.7→2.8.4、plugin-notification 2.3.3→2.8.0、
   plugin-http 2.5.9→2.8.3、plugin-clipboard-manager 2.3.2→2.5.0、plugin-fs 2.5.0→2.7.1。

环境侧（不进仓库）：`src-tauri/gen/android` 由 `tauri android init` 生成；
根 `build.gradle.kts` 里补了 exp1 同款的 `subprojects { buildToolsVersion = "36.0.0" }` ——
AGP 8.11 默认要 35.0.0，本机只有 36.0.0，而 `/opt/android-sdk` 不可写、`sdkmanager`（cmdline-tools 23.0）
在这台机器上一跑就崩（`AndroidCLI` 空指针），只能用这个绕法。

## 移动端实测发现的两个 CSS 问题（已修）

| 现象 | 原因 | 修法 |
|---|---|---|
| 底部导航被顶到屏幕外 | 移动端浏览器/WebView 里 `100vh` 是「大视口」：实测 `innerHeight=762` 而 `.app=818` | `height: 100dvh`（带 `100vh` 兜底） |
